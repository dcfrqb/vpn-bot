# Оплата с сайта без Telegram

Сайт передает UUID текущего аккаунта через внутренний API бота. Номер аккаунта и сумма из браузера не используются как источник прав. Тариф и цена берутся из каталога бота, перед созданием платежа цена повторно проверяется.

## Учет и выдача

- Действующие Telegram-аккаунты используют прежние CheckoutService и Fulfillment.
- Покупатели без Telegram получают записи `site_customers` и `site_orders`, отдельные аккаунты панели с проверяемой меткой владельца. Подставных Telegram ID нет.
- Заказ сохраняется до запроса ЮKassa, ключ идемпотентности `site:<UUID>`. Срок сохраняется до записи в панель. Повторное уведомление или потеря ответа не добавляют новый месяц.
- Pro выдает основную подписку и обход, 150 ГБ в месяц. Смена тарифа сохраняет срок. Ручные ограничения, чужие аккаунты и бессрочные подписки требуют проверки.
- Заказы одного аккаунта сериализуются advisory lock на отдельном соединении Postgres. Фоновая проверка восстанавливает незавершенную выдачу.
- Уведомления используют существующий webhook ЮKassa. Статус, сумма, валюта и принадлежность платежа перечитываются у провайдера. Тело уведомления служит только указателем.
- Частичные возвраты и спорные состояния переводятся в ручную проверку. Полный возврат уменьшает только выданное этим заказом время; новый тариф восстанавливается по оставшимся выполненным заказам. Ручные изменения срока после начала возврата требуют проверки.

После покупки без Telegram последующая привязка Telegram сохраняет выбранный веб-учет. Перенос такой подписки в учет бота этим изменением не реализован.

## Порядок включения

1. Применить Alembic до `r31_01_site_checkout`, проверить `alembic check`.
2. Развернуть код бота с выключенным checkout. Сохранить прежние образы и резервную копию БД.
3. Проверить debug со своим тестовым магазином или локальным симулятором. Тестовый магазин требует ключа `test_`; рабочий ключ отвергается в тестовом режиме.
4. После приемки владельцем включить на рабочем боте `SITE_CHECKOUT_ENABLED=true`, `SITE_COMMERCE_RECOVERY_ENABLED=true`, `SITE_PAYMENT_TEST_MODE=false`. Использовать существующие `YOOKASSA_SHOP_ID` и `YOOKASSA_API_KEY`, секрет не передавать сайту.
5. Сайт: `BOT_API_URL` на внутренний API бота, совпадающий внутренний токен, действующий доступ к панели и `SITE_CHECKOUT_ENABLED=true`. После проверки маршрутов включить сайт.
6. В действующей настройке уведомлений магазина сохранить прежний URL и события, дополнительно включить `refund.succeeded`. Не создавать второй webhook вместо бота. Резервный опрос выполненных платежей охватывает последние 31 день.
7. Выполнить согласованную владельцем настоящую покупку и проверить кабинет, срок и запись заказа. Реальная покупка не входит в локальный симулятор.

Для остановки новых продаж выключить checkout на сайте и боте. Фоновое восстановление уже оплаченных заказов оставлять включенным. Не откатывать добавочные таблицы с действующими заказами; старый код не обслуживает веб-покупки, нужен совместимый API до завершения всех заказов.

## Локальное демо

`scripts/site_checkout_demo.py` запускает реальную службу и внутренние маршруты с фиктивными провайдером и панелью. Только loopback, реальные ключи не читает, денег не списывает, рабочие VPN-аккаунты не меняет. Состояние симулятора теряется при остановке.

```sh
PYTHONPATH=src:. .venv/bin/uvicorn scripts.site_checkout_demo:app --host 127.0.0.1 --port 18050
```

API сайта: отдельная локальная БД, origin `http://127.0.0.1:13040`, cookie `demo_sid`, bot/panel URL `http://127.0.0.1:18050`, внутренний токен `local-checkout-demo`, checkout включен. SMTP, Google и Telegram для локального демо не нужны.

Web в development: `API_INTERNAL_URL=http://127.0.0.1:18040`, `NEXT_PUBLIC_CHECKOUT_DEMO_ORIGIN=http://127.0.0.1:18050`, порт 13040. Разрешение перехода в фиктивный банк отсутствует в production-сборке.
